# BG-Agent: бот проверки компаний

Проверка компании или ИП по ИНН/ОГРН в трёх источниках:

| Пакет | Источник | Что даёт |
|---|---|---|
| `pbnalog` | ФНС «Прозрачный бизнес», pb.nalog.ru | карточка юрлица или ИП |
| `rnp` | Реестр недобросовестных поставщиков, zakupki.gov.ru | записи РНП по ИНН, действует ли запись |
| `fssp` | Банк данных исполнительных производств ФССП | производства, остаток долга |
| `checks` | все три | сводный отчёт (dict/JSON) и флаги риска |

Пакеты источников и `checks` не зависят от Telegram: их же будет вызывать
веб-кабинет. Бот (`bot/`) только принимает запрос, пересылает капчи в чат и
форматирует отчёт.

```bash
python -m checks 7707083893 -o report.json   # полная проверка из консоли
```

## pb.nalog.ru

Модуль `pbnalog` получает по ИНН/ОГРН карточку юрлица или ИП из сервиса ФНС
«Прозрачный бизнес» (https://pb.nalog.ru). Официального API у сервиса нет,
модуль повторяет запросы веб-интерфейса.

## Как устроен обмен с сайтом

| Шаг | Запрос | Что получаем |
|---|---|---|
| 1 | `POST /search-proc.json` (`mode=search-ul` / `search-ip`, `queryUl`/`queryIp`=ИНН или ОГРН) | `{"ul": {"data": [...]}}` или `{"ip": {"data": [...]}}`, у каждой строки есть `token` |
| 2 | `POST /company-proc.json` (`token`, `method=get-request`) | `{"id": ..., "token": ...}` |
| 3 | `POST /company-proc.json` (`id`, `token`, `method=get-response`) | карточка в JSON; пока она готовится, ответ пустой, клиент повторяет запрос |

**Капча.** При частых запросах шаги 1–2 отвечают ошибкой с упоминанием капчи.
Тогда клиент открывает `/captcha-dialog.html`, берёт из ссылки на картинку
`/static/captcha.bin?...&a=<captchaToken>` токен, скачивает картинку, отдаёт её
решателю (`solver`), отправляет `POST /captcha-proc.json` (`captcha`, `captchaToken`)
и получает `pbCaptchaToken`, который подставляется в следующие запросы.
Капча цифровая, 6 знаков. Решатель подключается снаружи: ручной ввод,
сервис распознавания (RuCaptcha и т.п.) или своя модель.

**Лимиты.** Публичных лимитов нет; по опыту других разработчиков капча
появляется при частых запросах. По умолчанию клиент делает не больше одного
запроса в 1,5 секунды (`min_interval`).

**Доступ.** Сайты ФНС могут не открываться с зарубежных IP, запускать лучше
на сервере в РФ.

## Использование

```bash
pip install -r requirements.txt
python -m pbnalog 7707083893 -o card.json      # если спросит капчу, введите цифры с картинки captcha.png
```

```python
from pbnalog import PbNalogClient

async def solver(image: bytes) -> str:
    ...  # распознать 6 цифр

async with PbNalogClient(solver=solver) as pb:
    res = await pb.lookup("1027700132195")    # {"kind": "ul", "hit": {...}, "card": {...}}
    found = await pb.search("ромашка", kind="all")
```

## Реестр недобросовестных поставщиков (`rnp`)

`GET https://zakupki.gov.ru/epz/dishonestsupplier/search/results.html?searchString=<ИНН>`
возвращает HTML-выдачу ЕИС. Клиент разбирает блоки `registry-entry__form`:
номер и ссылку на карточку, закон (44-ФЗ / 223-ФЗ), пары «подпись — значение»
и даты (Включено, Обновлено, Исключено). Полнотекстовый поиск может зацепить
чужие записи, поэтому `check(inn)` оставляет только записи с этим ИНН.
Запись считается действующей, пока у неё нет даты исключения
(«Планируемая дата исключения» не в счёт). Капчи нет.

```bash
python -m rnp 7707083893
```

## ФССП (`fssp`)

Открытый API ФССП (api-ip.fssp.gov.ru) закрыт, клиент повторяет поиск со
страницы https://fssp.gov.ru/iss/ip:
`GET https://is.fssp.gov.ru/ajax_search?system=ip&is[extended]=1&is[variant]=...`.
Варианты: 1 — физлицо/ИП по ФИО (и дате рождения), 2 — юрлицо по наименованию,
3 — номер производства. **По ИНН сайт не ищет**, поэтому `checks` берёт
наименование или ФИО из карточки ФНС: юрлица фильтруются по точному совпадению
названия, а у ИП без даты рождения в выдаче могут оказаться тёзки (это
отмечается в отчёте).

Ответ — JSON/JSONP с HTML в поле `data`: таблица из 8 колонок (должник,
номер и дата ИП, исполнительный документ, дата и причина окончания, сервис,
предмет исполнения и сумма, отдел, пристав). Пустая колонка окончания —
производство ведётся. Если в HTML картинка `img#capchaVisual` (base64), её
решает `solver`, и запрос повторяется с `code=<ответ>`. Капча из кириллицы и цифр.

```bash
python -m fssp --legal "ООО РОМАШКА"
python -m fssp --person Иванов Иван Иванович --birth 01.01.1980
```

## Telegram-бот

```bash
pip install -r requirements.txt
BOT_TOKEN=<токен от @BotFather> python -m bot.main
```

Пользователь присылает ИНН или ОГРН, бот проверяет контрольную сумму,
прогоняет `checks` (ФНС → РНП → ФССП) и отвечает сводкой с флагами риска плюс
полным отчётом в JSON. Если сайт ФНС или ФССП просит капчу, бот присылает
картинку в чат и ждёт ответ от того же пользователя (2 минуты). Ошибка одного
источника не мешает остальным.

## Личный кабинет и API

Кабинет (`app/`) это сервис на FastAPI: регистрация по email, проверка по
ИНН/ОГРН, история проверок, сырой JSON каждого источника. Telegram-бот будет
работать через тот же API, поэтому проверки из бота и кабинета хранятся вместе.

```
браузер ─┐                         ┌─ ФНС «Прозрачный бизнес» (pbnalog)
         ├─ web (FastAPI) ─ Redis ─ worker (arq) ─┼─ РНП
бот ─────┘        │                 │             └─ ФССП
                  └──── PostgreSQL ─┘
```

- **Источники** (`app/sources/`) реализуют протокол `Source`: получают
  ИНН/ОГРН и ответы предыдущих источников, возвращают `SourceData` (краткую
  таблицу, сырой ответ и, если знают, название, ИНН, ОГРН). Ошибка одного
  источника не ломает проверку, она сохраняется в его строке.
- **Проверка** (`app/checks.py`) идёт фоном: статусы `queued → running →
  (captcha) → done/error`. Страница кабинета сама обновляется, пока проверка идёт.
- **Капча** (`app/captcha.py`): воркер кладёт картинку в Redis и ждёт ответа,
  кабинет показывает её пользователю (`GET/POST /api/checks/{id}/captcha`).
- **API**: `POST /api/checks`, `GET /api/checks`, `GET /api/checks/{id}`,
  `GET /api/checks/{id}/data/{source}`. Кабинет ходит с cookie-сессией, бот
  с заголовками `X-Bot-Token` (общий секрет `BOT_API_TOKEN`) и `X-Telegram-Id`.
  Документация: `/docs`.

Локально, без Redis и Postgres (проверки идут в процессе, база в SQLite):

```bash
pip install -r requirements.txt
uvicorn app.main:app --reload    # http://127.0.0.1:8000
```

На сервере (VPS с российским IP, иначе сайты ФНС не откроются):

```bash
cp .env.example .env     # заполнить домен, пароли, SECRET_KEY
docker compose up -d --build
```

Поднимутся web, worker, PostgreSQL, Redis и Caddy, который сам выпустит
HTTPS-сертификат для домена из `DOMAIN`.

## Тесты

```bash
pip install -r requirements-dev.txt
python -m pytest -q
```

Тесты идут на имитации сайтов: живые ответы pb.nalog.ru, zakupki.gov.ru и
is.fssp.gov.ru пока не проверены (из облачной среды разработки эти сайты
недоступны). При первом запуске с российского IP нужно сверить состав полей
карточки ФНС, разметку выдачи РНП и формат ответа ФССП.
