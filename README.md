# BG-Agent: бот проверки компаний

Проверка компании или ИП по ИНН/ОГРН в трёх источниках:

| Пакет | Источник | Что даёт |
|---|---|---|
| `pbnalog` | ФНС «Прозрачный бизнес», pb.nalog.ru | карточка юрлица или ИП |
| `rnp` | Реестр недобросовестных поставщиков, zakupki.gov.ru | записи РНП по ИНН, действует ли запись |
| `fssp` | Банк данных исполнительных производств ФССП | производства, остаток долга |
| `checks` | все три | сводный отчёт (dict/JSON) и флаги риска |

Пакеты источников и `checks` не зависят от Telegram: их же будет вызывать
веб-кабинет. Бот (`bot/`) только принимает запрос, пересылает капчи в чат и
форматирует отчёт.

```bash
python -m checks 7707083893 -o report.json   # полная проверка из консоли
```

## pb.nalog.ru

Модуль `pbnalog` получает по ИНН/ОГРН карточку юрлица или ИП из сервиса ФНС
«Прозрачный бизнес» (https://pb.nalog.ru). Официального API у сервиса нет,
модуль повторяет запросы веб-интерфейса.

## Как устроен обмен с сайтом

| Шаг | Запрос | Что получаем |
|---|---|---|
| 1 | `POST /search-proc.json` (`mode=search-ul` / `search-ip`, `queryUl`/`queryIp`=ИНН или ОГРН) | `{"ul": {"data": [...]}}` или `{"ip": {"data": [...]}}`, у каждой строки есть `token` |
| 2 | `POST /company-proc.json` (`token`, `method=get-request`) | `{"id": ..., "token": ...}` |
| 3 | `POST /company-proc.json` (`id`, `token`, `method=get-response`) | карточка в JSON; пока она готовится, ответ пустой, клиент повторяет запрос |

**Капча.** При частых запросах шаги 1–2 отвечают ошибкой с упоминанием капчи.
Тогда клиент открывает `/captcha-dialog.html`, берёт из ссылки на картинку
`/static/captcha.bin?...&a=<captchaToken>` токен, скачивает картинку, отдаёт её
решателю (`solver`), отправляет `POST /captcha-proc.json` (`captcha`, `captchaToken`)
и получает `pbCaptchaToken`, который подставляется в следующие запросы.
Капча цифровая, 6 знаков. Решатель подключается снаружи: ручной ввод,
сервис распознавания (RuCaptcha и т.п.) или своя модель.

**Лимиты.** Публичных лимитов нет; по опыту других разработчиков капча
появляется при частых запросах. По умолчанию клиент делает не больше одного
запроса в 1,5 секунды (`min_interval`).

**Доступ.** Сайты ФНС могут не открываться с зарубежных IP, запускать лучше
на сервере в РФ.

## Использование

```bash
pip install -r requirements.txt
python -m pbnalog 7707083893 -o card.json      # если спросит капчу, введите цифры с картинки captcha.png
```

```python
from pbnalog import PbNalogClient

async def solver(image: bytes) -> str:
    ...  # распознать 6 цифр

async with PbNalogClient(solver=solver) as pb:
    res = await pb.lookup("1027700132195")    # {"kind": "ul", "hit": {...}, "card": {...}}
    found = await pb.search("ромашка", kind="all")
```

## Реестр недобросовестных поставщиков (`rnp`)

`GET https://zakupki.gov.ru/epz/dishonestsupplier/search/results.html?searchString=<ИНН>`
возвращает HTML-выдачу ЕИС. Клиент разбирает блоки `registry-entry__form`:
номер и ссылку на карточку, закон (44-ФЗ / 223-ФЗ), пары «подпись — значение»
и даты (Включено, Обновлено, Исключено). Полнотекстовый поиск может зацепить
чужие записи, поэтому `check(inn)` оставляет только записи с этим ИНН.
Запись считается действующей, пока у неё нет даты исключения
(«Планируемая дата исключения» не в счёт). Капчи нет.

```bash
python -m rnp 7707083893
```

## ФССП (`fssp`)

Открытый API ФССП (api-ip.fssp.gov.ru) закрыт, клиент повторяет поиск со
страницы https://fssp.gov.ru/iss/ip:
`GET https://is.fssp.gov.ru/ajax_search?system=ip&is[extended]=1&is[variant]=...`.
Варианты: 1 — физлицо/ИП по ФИО (и дате рождения), 2 — юрлицо по наименованию,
3 — номер производства. **По ИНН сайт не ищет**, поэтому `checks` берёт
наименование или ФИО из карточки ФНС: юрлица фильтруются по точному совпадению
названия, а у ИП без даты рождения в выдаче могут оказаться тёзки (это
отмечается в отчёте).

Ответ — JSON/JSONP с HTML в поле `data`: таблица из 8 колонок (должник,
номер и дата ИП, исполнительный документ, дата и причина окончания, сервис,
предмет исполнения и сумма, отдел, пристав). Пустая колонка окончания —
производство ведётся. Если в HTML картинка `img#capchaVisual` (base64), её
решает `solver`, и запрос повторяется с `code=<ответ>`. Капча из кириллицы и цифр.

```bash
python -m fssp --legal "ООО РОМАШКА"
python -m fssp --person Иванов Иван Иванович --birth 01.01.1980
```

## Telegram-бот

```bash
pip install -r requirements.txt
BOT_TOKEN=<токен от @BotFather> python -m bot.main
```

Пользователь присылает ИНН или ОГРН, бот проверяет контрольную сумму,
прогоняет `checks` (ФНС → РНП → ФССП) и отвечает сводкой с флагами риска плюс
полным отчётом в JSON. Если сайт ФНС или ФССП просит капчу, бот присылает
картинку в чат и ждёт ответ от того же пользователя (2 минуты). Ошибка одного
источника не мешает остальным.

## Личный кабинет и API

Кабинет (`app/`) это сервис на FastAPI: регистрация по email, проверка по
ИНН/ОГРН, история проверок, сырой JSON каждого источника. Telegram-бот будет
работать через тот же API, поэтому проверки из бота и кабинета хранятся вместе.

```
                                                  ┌─ DaData (карточка, основной)
браузер ─┐                                        ├─ ФНС «Прозрачный бизнес» (pbnalog)
         ├─ web (FastAPI) ─ Redis ─ worker (arq) ─┼─ ЕФРСБ, 19.28 КоАП, открытые данные ФНС
бот ─────┘        │                 │             └─ РНП, ФССП
                  └──── PostgreSQL ─┘
```

- **Источники** (`app/sources/`) реализуют протокол `Source`: получают
  ИНН/ОГРН и ответы предыдущих источников, возвращают `SourceData` (краткую
  таблицу, сырой ответ и, если знают, название, ИНН, ОГРН). Ошибка одного
  источника не ломает проверку, она сохраняется в его строке.
- **Проверка** (`app/checks.py`) идёт фоном: статусы `queued → running →
  (captcha) → done/error`. Страница кабинета сама обновляется, пока проверка идёт.
- **Капча** (`app/captcha.py`): воркер кладёт картинку в Redis и ждёт ответа,
  кабинет показывает её пользователю (`GET/POST /api/checks/{id}/captcha`).
- **API**: `POST /api/checks`, `GET /api/checks`, `GET /api/checks/{id}`,
  `GET /api/checks/{id}/data/{source}`. Кабинет ходит с cookie-сессией, бот
  с заголовками `X-Bot-Token` (общий секрет `BOT_API_TOKEN`) и `X-Telegram-Id`.
  Документация: `/docs`.

Локально, без Redis и Postgres (проверки идут в процессе, база в SQLite):

```bash
pip install -r requirements.txt
uvicorn app.main:app --reload    # http://127.0.0.1:8000
```

На сервере (VPS с российским IP, иначе сайты ФНС не откроются):

```bash
cp .env.example .env     # заполнить домен, пароли, SECRET_KEY
docker compose up -d --build
```

Для пробы на сервере от 512 МБ памяти есть облегчённая установка одной
командой, без Docker, PostgreSQL и Redis (SQLite, uvicorn под systemd, Caddy):
`deploy/install-lite.sh <домен>`, подробности в начале скрипта.

Полная версия: поднимутся web, worker, PostgreSQL, Redis и Caddy, который сам выпустит
HTTPS-сертификат для домена из `DOMAIN`.

## CRM брокера: сделки и клиенты

Кабинет работает в двух ролях. **Клиент** (роль `client`, по умолчанию) сам
регистрируется, проверяет контрагентов, подбирает закупки и нажимает «Нужна
гарантия». **Сотрудник** (`manager` или `admin`) видит раздел CRM:

- **Сделки** (`/crm/deals`): воронка по гарантиям с этапами «Новая → Сбор
  документов → В банках → Одобрена → Выдана / Отказ». Кнопка «Нужна гарантия»
  у клиента сама заводит сделку (по одной на каждый вид гарантии), клиент видит
  её этап у себя на странице «Закупки». В сделке: сумма, комиссия брокера и
  список банков со статусом, ставкой и стоимостью для клиента. Первый банк
  переводит сделку в «В банках», одобрение банка в «Одобрена», выдача в «Выдана».
- **Клиенты** (`/crm/clients`): карточка компании (название и ОГРН
  подтягиваются из проверки по ИНН), откуда пришёл клиент, контакты, все его
  проверки и сделки, кнопка «Проверить сейчас».
- **Журнал**: заметки и звонки сотрудников плюс автоматические записи о смене
  этапов, банках и проверках, по клиенту и по каждой сделке.

- **Задачи** (`/crm/tasks`): просроченные, на сегодня и дальше; у клиента и у
  сделки свой список. Ответственный за клиента получает его задачи. Когда у
  выданной гарантии (поле «Гарантия действует до») остаётся 30 дней, задача
  «предложить новую» появляется сама.
- **Напоминания в Telegram**: на странице «Задачи» кнопка «Подключить
  Telegram» даёт ссылку на бота; в срок задачи бот присылает напоминание.
  Нужны `BOT_TOKEN`, `BOT_USERNAME` и `BOT_API_TOKEN` в `.env`, бот ходит в
  кабинет по `CABINET_URL`. Рассылку делает `python -m app.crm_tasks` каждые
  5 минут (в облегчённой установке это таймер systemd, в Docker — воркер).

- **Аналитика** (`/crm/reports`): за месяц, прошлый месяц, 3 или 12 месяцев:
  новые сделки, выдачи и комиссия, доля выдач, воронка, комиссия по месяцам,
  разрез по источникам клиентов, продуктам, менеджерам и банкам (доля
  одобрений, средняя стоимость). Менеджер видит цифры по своим клиентам.
- **Excel**: выгрузка клиентов и сделок (`/crm/clients.xlsx`,
  `/crm/deals.xlsx`) и загрузка списка клиентов из Excel/CSV на странице
  «Клиенты» (колонки «ИНН», «Наименование», «Источник», «Контакт», «Телефон»,
  «Email»; уже известные ИНН пропускаются).

Администраторы задаются в `.env`: `ADMIN_EMAILS=boss@example.ru` (роль
выдаётся при входе). Остальным сотрудникам администратор выдаёт роль на странице «Сотрудники»
(`/crm/staff`, сотрудник сначала регистрируется в кабинете) или командой
`python -m app.roles email@example.ru manager`.

Доступ: администратор видит всех клиентов, сделки и задачи и может передавать
клиентов. Менеджер видит своих клиентов и тех, у кого ещё нет ответственного
(например, заявки, пришедшие из кабинета), может взять такого клиента себе;
клиент, которого завёл менеджер, сразу закреплён за ним. Если снять с
сотрудника роль, его клиенты и открытые задачи возвращаются в общий список.

## Согласия, уведомления и рассылки

Устроено под требования закона «О рекламе» (ст. 18: реклама по email, SMS и в
мессенджерах только с предварительного согласия, доказывает его отправитель) и
152-ФЗ. Это техническая схема, юридические тексты стоит показать юристу.

- **Согласие на обработку ПДн** обязательно при регистрации, отдельной
  галочкой со ссылкой на отдельный текст (`/legal/pd`). **Согласие на рекламу**
  необязательное, отдельной галочкой (`/legal/ads`). Для каждого согласия
  хранится канал и адрес, время, источник, текст в той редакции, IP и браузер;
  отзыв не стирает запись, а отмечает время и способ отзыва.
- **Настройки** (`/settings`): клиент включает и выключает рекламу по email и
  в Telegram, уведомления по своим заявкам и привязывает Telegram.
- **Отписка**: ссылка `/u/<токен>` в каждом рекламном письме (и заголовок
  `List-Unsubscribe`), команда `/stop` в боте, кнопка в настройках, отзыв
  сотрудником в карточке клиента.
- **Уведомления** по сделке клиента (отправлена в банки, одобрена, выдана,
  отказ) не реклама: уходят без согласия на рекламу, в Telegram, если он
  привязан, иначе на email.
- **Согласие, полученное вне кабинета** (подписанная анкета, письмо) сотрудник
  вносит в карточке клиента, источник обязателен.
- **Рассылки** (`/crm/campaigns`, только администратор): черновик → проверка
  получателей и текста → отправка с подтверждением. Получатели — только
  действующие согласия на рекламу по каналу, с фильтром по сегменту (все, с
  выданной гарантией, со сделкой в работе, без сделок, по источнику). В каждое
  сообщение добавляются «Реклама», рекламодатель, erid (если реклама
  зарегистрирована в ОРД) и способ отписаться. Перед отправкой каждого
  сообщения согласие проверяется ещё раз.
- Доставка: очередь `outbox`, её разбирает тот же `python -m app.crm_tasks`
  (каждые 5 минут). Email уходит через SMTP российского сервиса
  (`SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`, `SMTP_FROM`),
  Telegram через `BOT_TOKEN`. Реквизиты для текстов согласий и пометки
  «Реклама»: `OPERATOR_NAME`, `OPERATOR_INN`, `OPERATOR_ADDRESS`. Для ссылки
  «Отписаться» нужен `PUBLIC_URL` или `DOMAIN`.

## Карточка компании из DaData

Основной источник карточки юрлица или ИП в кабинете и проверках — DaData
(официальный API `findById/party`, пакет `dadata`): без капчи, быстро, формат
ответа стабилен. pb.nalog.ru (пакет `pbnalog`) остаётся дополнительным
источником для того, чего в DaData нет, и запасным, если DaData не ответила.

Что показывается зависит от тарифа DaData:

| Тариф | Что есть |
|---|---|
| Бесплатный (10 000 запросов в сутки) | реквизиты, статус, даты, адрес, ОКВЭД, руководитель (ФИО и должность без ИНН) |
| «Расширенный» | + численность, налоговый режим, все ОКВЭД, налоговая/ПФР/ФСС |
| «Максимальный» | + учредители и доли, руководители с ИНН, финансы, недоимки и штрафы, лицензии, правопреемники, признак дисквалификации |

Тревожные признаки (ликвидация, банкротство, реорганизация, недостоверность,
дисквалифицированные в руководстве, недоимки) выносятся в строку «Внимание».

Связанные лица для проверок банкротства, 19.28 КоАП и дисквалификации
собираются в `app/sources/parties.py`: сначала учредители и руководители из
DaData, затем то, что нашлось в карточке pb.nalog.ru. На бесплатном тарифе
учредителей в DaData нет, поэтому по умолчанию pb.nalog.ru опрашивается всегда.

Настройки (в `.env` или `/opt/bg-agent/env` на сервере):

- `DADATA_API_KEY` — ключ из личного кабинета dadata.ru (раздел «API-ключи»).
  Без ключа источник DaData не подключается, всё работает как раньше.
- `DADATA_SECRET` — секретный ключ; для карточки компании не нужен.
- `PBNALOG_MODE` — `always` (по умолчанию) дополнять DaData; `fallback`
  обращаться к pb.nalog.ru только если DaData не нашла компанию или ответила
  ошибкой (меньше капчи); `off` не обращаться.

Если DaData ответила, а pb.nalog.ru отказал (капчу не ввели, сайт недоступен,
блокировка), проверка не падает: карточка показывается по DaData, а в блоке
pb.nalog.ru стоит пометка «не ответил». Проверки банкротства, 19.28 КоАП и
дисквалификации в этом случае берут связанных лиц только из DaData. Ошибкой
источника отказ pb.nalog.ru остаётся, только если DaData не ответила.

Ответы DaData кешируются в памяти процесса на час, чтобы повторные проверки
одной компании не тратили лимит.

```bash
# на сервере: ключ в настройки и проверка
echo 'DADATA_API_KEY=ваш_ключ' | sudo tee -a /opt/bg-agent/env
sudo systemctl restart bg-agent
sudo -u bg bash -c 'set -a; . /opt/bg-agent/env; cd /opt/bg-agent/app-src &&
  /opt/bg-agent/venv/bin/python -m dadata 7707083893'
```

Telegram-бот пока ходит в pb.nalog.ru напрямую; когда он переедет на API
кабинета, получит карточку DaData автоматически.

## Проверка банкротства (ЕФРСБ)

Пакет `bankrot` ищет сведения в Едином федеральном реестре сведений о
банкротстве (bankrot.fedresurs.ru) и на Федресурсе (fedresurs.ru). В кабинете
это источник `bankrot`, он идёт после ФНС и проверяет:

- **саму компанию или физлицо/ИП** по ИНН (12-значный ИНН физлица тоже можно
  вводить: если его нет в «Прозрачном бизнесе», имя берётся из ЕФРСБ);
- **намерения кредиторов** подать на банкротство компании (сообщения на
  Федресурсе за 15 дней до иска, ранний сигнал, когда дела ещё нет);
- **связанных лиц** из карточки ФНС: руководителей, учредителей и компании,
  которые в карточке вложены в них (другие компании руководителя и т.п.).
  Берутся только лица с корректным ИНН, по ФИО без ИНН не ищем, чтобы не
  получить однофамильцев. Не больше 30 лиц на проверку.

Совпадение засчитывается только по точному ИНН/ОГРН. Процедура считается
завершённой, если в статусе дела есть «завершено», «прекращено» и т.п.; в отчёте
такие строки помечены «Было банкротство». Номер дела выводится, саму
картотеку арбитражных дел (kad.arbitr.ru) не опрашиваем: у неё нет открытого
API и стоит защита от ботов.

Официальный API ЕФРСБ платный, поэтому клиент повторяет запросы поиска на
сайте (без капчи, нужен заголовок Referer, не чаще запроса в секунду). Из
облака Claude сайты недоступны, формат ответов **не сверен с живым сайтом**,
тесты работают на имитации. Проверить с сервера в РФ:

```bash
python -m bankrot 7707083893 --json                    # компания
python -m bankrot 500100732259                         # физлицо по ИНН
python -m pbnalog 7707083893 -o card.json && python -m bankrot 7707083893 --card card.json
curl -s -H 'Referer: https://bankrot.fedresurs.ru/' \
  'https://bankrot.fedresurs.ru/backend/cmpbankrupts?searchString=<ИНН банкрота>&isActiveLegalCase=null&limit=15&offset=0'
```

Если поля в ответе называются иначе, поправить разбор в `bankrot/client.py`
(`parse_bankruptcy`) и роли в `bankrot/parties.py`.

## Реестр 19.28 КоАП (незаконное вознаграждение)

Пакет `koap1928` проверяет, привлекалась ли компания к ответственности по
ст. 19.28 КоАП (незаконное вознаграждение от имени юрлица). Это стоп-фактор для
гарантии по 44-ФЗ: по п. 7.1 ч. 1 ст. 31 такая компания два года не допускается
к закупкам. В кабинете это источник `koap1928`, он идёт после ФНС и банкротства.

**Откуда данные.** Реестр раньше вела Генпрокуратура на своём сайте, с 30.07.2021
он там не размещается. Сейчас сведения публикуются в ЕИС файлом Excel в разделе
«Документы» («Информация о привлечении участника закупки к административной
ответственности по ст. 19.28 КоАП»):
https://zakupki.gov.ru/epz/main/public/document/view.html?searchString=&sectionId=2369&strictEqual=false
Колонки: ИНН, ОГРН, КПП, наименование, тип участника, суд, номер дела, дата
постановления, дата вступления в силу. Капчи и токена нет, файл около 1000 строк.

**Как работает.** Клиент читает страницу раздела, находит ссылку на файл,
скачивает его и держит в памяти 12 часов. Поиск только по точному ИНН/ОГРН
(в реестре есть однофамильные компании). Два года запрета считаются от даты
вступления постановления в силу, если её нет, от даты постановления. В отчёте:
«запрещено до ДД.ММ.ГГГГ», «был в реестре, запрет истёк» или «не найден».
Дополнительно проверяются компании из карточки ФНС (учредители-юрлица, другие
компании руководителя и т.п.), физлиц в реестре нет.

Из облака Claude ЕИС недоступна, **ни страница, ни файл не сверены с живым
сайтом**, тесты работают на имитации. Проверить с сервера в РФ:

```bash
python -m koap1928 --dump              # скачать файл и показать, как разобраны первые записи
python -m koap1928 7707083893          # проверка по ИНН или ОГРН
python -m koap1928 7707083893 --file reestr.xlsx   # по файлу, скачанному вручную
```

Если ссылка на файл не находится, задать `KOAP1928_URL` (прямая ссылка
`.../downloadDocument.html?id=...`) или положить файл и указать `KOAP1928_FILE`.
`KOAP1928_CACHE` сохраняет последнюю удачную копию на диск: если ЕИС не ответит,
проверка пройдёт по ней с пометкой в отчёте. Если заголовки колонок другие,
поправить `COLUMNS` в `koap1928/registry.py`.

## Блокировки счетов и ограничения на открытие счетов

Источник кабинета `accblock` (пакет `accblock`) идёт сразу после карточки
компании. Проверяется только по ИНН (для ОГРН ИНН берётся из карточки).

**1. ФНС: действующие решения о приостановлении операций по счетам.**
Сервис https://service.nalog.ru/bi.do. Пока решение действует, операции по
счетам остановлены, а банк не вправе открывать организации или ИП новые счета
(п. 12 ст. 76 НК РФ). Это и есть «ограничение на открытие счетов». Форме нужен
ИНН и БИК банка; БИК берётся из `FNS_BI_BIK` (по умолчанию Сбербанк 044525225).
У сервиса бывает капча: она показывается пользователю в кабинете, как у
pb.nalog.ru, и не обходится.

**2. Банк России, «Знай своего клиента» (ЗСК).** С 1 октября 2024 года на
https://www.cbr.ru/counteraction_m_ter/platform_zsk/proverka-po-inn/ любой может
узнать, отнесена ли компания или ИП к группе высокого уровня риска («красная
зона»: банки ограничивают операции и открытие счетов по 115-ФЗ). Подробностей
ЦБ не даёт, только «да/нет». Как форма отправляет запрос, из облака не видно,
поэтому автоматический запрос включается переменной `CBR_ZSK_URL`. Пока она не
задана, в отчёте ссылка на форму для ручной проверки.

**Чего нет в открытом доступе:** отказы банков в открытии счёта и блокировки
самим банком по 115-ФЗ (сведения закрыты, их видит только сам клиент), аресты
счетов приставами (видны косвенно через ФССП, PR #3).

**Если источник не ответил,** проверка не падает: в отчёте пометка
«Не удалось проверить блокировки счетов» (жёлтым) и ссылки на ручную проверку,
остальные источники показываются как обычно.

Из облака Claude сайты ФНС и ЦБ недоступны, **формат ответов не сверен**, тесты
на имитации. Проверить с сервера в РФ:

```bash
python -m accblock 7707083893 --dump   # капча сохранится в файл, цифры ввести в терминале
python -m accblock --zsk-page          # скачать форму ЦБ и показать, куда она отправляет запрос
```

Что сверить: (1) в `--dump` виден список решений — если поля называются иначе,
поправить `_FIELDS` в `accblock/fns.py`; (2) по ИНН с известной блокировкой
решения находятся при БИК не того банка, где счёт (то есть сервис отдаёт
решения по всем банкам). Если нет — указать в `FNS_BI_BIK` основной банк
клиентов; (3) по `--zsk-page` найти адрес запроса формы ЦБ и прописать
`CBR_ZSK_URL` (`{inn}` в адресе заменяется на ИНН). Если форма ЦБ с капчей,
оставить ручную проверку.

## Административная и уголовная ответственность: что проверяется

Только официальные открытые источники, без обхода капчи. В кабинете идут после ФНС:

| Источник | Что даёт | Откуда |
|---|---|---|
| `koap1928` | ст. 19.28 КоАП (незаконное вознаграждение), запрет на закупки 2 года | файл ЕИС, см. выше |
| `disqualified` | дисквалификация (ст. 3.11 КоАП) руководителей и учредителей-физлиц из карточки ФНС, а также лиц, дисквалифицированных из самой компании | открытые данные ФНС `7707329152-registerdisqualified` |
| `taxoffence` | штрафы за налоговые правонарушения (НК РФ) за прошлый год | открытые данные ФНС `7707329152-taxoffence` |
| `fssp` (PR #3) | неоплаченные административные штрафы и уголовные штрафы как исполнительные производства | ФССП |
| `rnp` (PR #3) | реестр недобросовестных поставщиков | ЕИС |

Наборы ФНС скачиваются целиком в `FNS_OPENDATA_DIR` (ссылка на свежий файл
берётся из паспорта `nalog.gov.ru/opendata/<код>/meta.csv`), проверяются раз в
сутки и перекачиваются, только если ссылка сменилась. Налоговые правонарушения —
большой архив XML, он один раз раскладывается в SQLite рядом с архивом.
В реестре дисквалифицированных нет ИНН человека, поэтому совпадение по ФИО
помечено как требующее сверки даты рождения.

Из облака сайты ФНС недоступны, **форматы паспортов и файлов не сверены**,
тесты на имитации. Если заголовки колонок другие, поправить `COLUMNS` в
`fnsdata/disqualified.py` и разбор в `fnsdata/taxoffence.py`.

**Чего нет в открытом доступе:**

- **Уголовная ответственность.** Единого открытого реестра судимостей нет (это
  сведения МВД, справка выдаётся только самому человеку). Юрлица в РФ к уголовной
  ответственности не привлекаются. Приговоры публикуются на сайтах судов общей
  юрисдикции (ГАС «Правосудие», sudrf.ru), но там капча и защита от ботов, а поиск
  по ФИО даёт однофамильцев, поэтому автоматически не опрашиваем.
- **Административные штрафы в целом.** Сводного реестра нет: ГИС ГМП закрыта, а дела
  в арбитражных судах (kad.arbitr.ru) и судах общей юрисдикции защищены от ботов.
  Неоплаченные штрафы видны через ФССП, решения ФАС — на br.fas.gov.ru (можно
  добавить отдельно).

## Оформление кабинета (бренд TenFin)

Все цвета, шрифты и компоненты — в одном файле `app/static/css/tenfin.css`, палитра собрана в переменных `:root`

- Логотип в шапке — `app/static/brand/logo.svg` (вариант для тёмного фона), значок вкладки — `app/static/brand/favicon.svg`.

- Шрифты Unbounded (заголовки) и Manrope (текст) лежат в `app/static/fonts/` и раздаются самим кабинетом,
  без запросов к Google Fonts.
- Базовый шаблон — `app/templates/base.html`: шапка с меню (на телефоне сворачивается в кнопку «Меню»), подвал.
- На телефоне таблицы складываются в карточки строк; таблицы с классом `keep` остаются таблицами
  (широкие — внутри `.table-scroll` с горизонтальной прокруткой).
- Скриншоты экранов — `docs/design/`.

## Подбор закупок для клиентов

Страница «Закупки» в кабинете: клиент указывает коды ОКПД2, регионы заказчиков и
диапазон НМЦК (или загружает выгрузку своих прошлых контрактов из ЕИС), и видит
подходящие закупки 44-ФЗ, 223-ФЗ и капремонта по ПП РФ 615 (185-ФЗ) с суммами
обеспечения заявки, исполнения и гарантийных обязательств. Кнопка «Нужна гарантия»
создаёт заявку брокеру.

Ключевые слова ищутся с учётом словоформ (стемминг Snowball) и словаря синонимов
отрасли (`tenders/keywords.py`): «кровля» найдёт «кровельные работы» и «ремонт крыши»,
`асфальт|щебень` — любое из слов, `-проект` — минус-слово. Всё считается на нашем
сервере, во внешние нейросети ничего не уходит.

**Подбор по смыслу.** Клиент описывает своими словами, что делает («ремонт мягкой
кровли, гидроизоляция»), и в подборку попадают закупки с близким по смыслу предметом,
даже без совпадения слов. Векторы текстов считает локальная модель
`paraphrase-multilingual-MiniLM-L12-v2` через fastembed (ONNX, без PyTorch, ~220 МБ на
диске, ~400 МБ памяти во время расчёта). Модель грузится только в фоновых задачах:
векторы закупок — после утренней загрузки, векторы описаний — таймером
`bg-agent-embed.timer` раз в 15 минут; веб-кабинет только сравнивает готовые векторы.
Включить на сервере:

```bash
sudo -u bg /opt/bg-agent/venv/bin/pip install -r /opt/bg-agent/app-src/requirements-ml.txt
echo 'EMBED_MODEL=sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2' | sudo tee -a /opt/bg-agent/env
sudo systemctl restart bg-agent && sudo systemctl start bg-agent-embed
```

Порог похожести — `EMBED_THRESHOLD` (по умолчанию 0.6; больше — строже).

Закупка подходит, если совпал код ОКПД2, ключевое слово или смысл описания;
минус-слова исключают её в любом случае.

Данные берутся только официально: анонимный ФТП ЕИС закрыт с 2025 года, поэтому
пакет `tenders` ходит в сервис отдачи документов ЕИС (getDocsIP) по токену.
Токен получают на https://zakupki.gov.ru/pmd/auth/welcome через Госуслуги
(«потребитель машиночитаемых данных», тип «Физическое лицо, ИП»).
Сервис открывается только с российских IP.

```bash
# на сервере: токен в настройки и проверка доступа
sudo nano /opt/bg-agent/env                 # добавить строку EIS_TOKEN=...
sudo systemctl restart bg-agent
sudo -u bg bash -c 'set -a; . /opt/bg-agent/env; cd /opt/bg-agent/app-src &&
  /opt/bg-agent/venv/bin/python -m tenders --region 77 --limit 5'
```

Каждое утро в 05:30 по Москве таймер `bg-agent-tenders.timer` запускает
`python -m app.tenders_sync`: скачивает вчерашние извещения по регионам из
профилей клиентов. Вручную: `systemctl start bg-agent-tenders`, журнал:
`journalctl -u bg-agent-tenders`. Если извещения не разбираются,
`python -m tenders --region 77 --raw /tmp/eis` сохранит сырые ответы для сверки.

Виды документов по законам заданы в `tenders/eis.py` (`DOC_TYPES`). Название вида
для ПП РФ 615 (`pprf615NotificationEF`) с живой ЕИС не сверено; если сервис его не
примет, в журнале будет ошибка, а 44-ФЗ и 223-ФЗ загрузятся как обычно. Поправить
без выпуска кода можно переменной в env:
`EIS_DOC_TYPES=615-ПП=PRIZ:pprf615NotificationEF2020` (через `;` для нескольких законов).
